# CLAUDE.md

Guidance for AI assistants working in this repository. Read this before changing code.

## What this project is

A consumer wine **discovery and learning game**: *"A game that learns your palate while teaching you about wine."*
It is meant to feel like a game and a discovery experience, not a wine database, a rating app, or a shopping app.

Target loop: `DISCOVER → SWIPE → PREDICT → DRINK → RECORD → LEARN → DISCOVER AGAIN`.

**This repository is the current web prototype** (a phone-first browser app). It is not the planned native iOS/Android app.
The long-term plan and the open questions are in `docs/ARCHITECTURE_PLAN.md`. Where the prototype and the product vision
differ, see "Prototype vs. product vision" below. Do not silently "fix" one to match the other.

## Tech stack and how it runs

- **No build step, no package manager, no bundler, no tests directory.** Plain static files: `index.html` plus native ES modules (`*.js`) in the repo root.
- **Backend: Supabase** (Postgres + row-level security + auth + storage + one Edge Function `find-photos`). The client library is kept in the repository (`vendor/supabase.js`, loaded first so the app opens offline) with the CDNs (`esm.sh`, `jsdelivr`) as fallbacks, see `app.js`.
- **Config:** `config.js` exports `SUPABASE_URL` and `SUPABASE_KEY`. Both are intentionally public (publishable/anon key, protected by RLS). **Never** put a `service_role`/secret key in this repo or in any client file.
- **Database schema/migrations are NOT in this repo.** Code references "database update N" in comments (e.g. update 21, 27), meaning SQL applied out of band in Supabase. If you need a table or column that does not exist, say so and describe the SQL; do not assume it exists. The tables/RPCs/views the client uses are visible by grepping `data.js` for `.from("` and `.rpc("`.
- **Run locally:** serve the directory with any static server (e.g. `python3 -m http.server 8000`) and open it in a phone-width browser. There is no `npm`/`make` command. The app needs network access to Supabase the first time; after that it can open offline (convention 22).
- **Hosting/deploy:** GitHub Pages, published by `.github/workflows/pages.yml` (kept the same on the main working branch and on `vwm`): the main working branch at the site's address and the `vwm` branch under `/vwm/`, copied as they are (no build). Pages' source must be set to "GitHub Actions". Both versions share one web origin, so they share the phone's saved settings, sign-in and offline copy (same database, so this is intended); their service-worker caches are kept apart by name (`wine-app-` and `vwm-app-` in `sw.js`).

## Critical conventions

1. **Cache-busting version query strings.** Every import carries `?v=N` (e.g. `./data.js?v=15`) and `index.html` loads `app.js?v=33`. Browsers cache ES modules aggressively. **When you change a module, bump its `?v=` everywhere it is imported** (grep for the filename), and bump `app.js?v=` in `index.html` if `app.js` changed. Mismatched versions cause stale or broken loads. Commit history ("increment app version to 30") shows this is the established practice.
2. **Layering:** put rules in a pure file, Supabase calls in `data.js`, HTML in `views.js`, wiring in `app.js` or a feature controller. Keep pure files free of `document`, `fetch`, `localStorage` and Supabase imports.
3. **Escape all interpolated text** in HTML strings with `esc()` from `logic.js`. Views build HTML strings; untrusted wine/user text must never be interpolated raw.
4. **Storage access is wrapped in try/catch** (see the `get`/`set` helpers in `app.js`). Keep it that way (private browsing, blocked storage).
5. **Style of code:** small, heavily commented files; comments explain *why* in plain language and open with a header describing the file's job. Match this. The code uses double quotes, semicolons, `const`/arrow functions, and section dividers like `// ------- name`.
6. **Single-hop data rule:** the app reads curated rows/views (`v_catalog_cards`, `v_journal_entries`, `v_user_wine_state`, `v_wine_prices`, `v_wine_crowd`) rather than joining on the client.
7. **Consent/age gate:** the app requires 21+ attestation and accepted terms (`consent.js`, `CONSENT_VERSION`). Change `CONSENT_VERSION` whenever the terms wording changes. Do not bypass the gate. **The owner started the pre-testing review on 2026-10-07**: **`privacy.html` is the one place the terms and privacy policy are written** (page title "Terms and privacy policy"); it is the owner's ideal draft for the lawyers (`docs/PRIVACY_DRAFT_NOTES.md`). `consent.js` shows two ticks, "I am 21 or older" and "I accept the terms and conditions" (the words link to `privacy.html`), with a small scrolling window between them that is an iframe of `privacy.html?embed=1` (the page hides its back link in embed mode), so the terms text is never copied into `consent.js`; keep that window modest in height (`.termsbox`) so the logo and other design have room. **Do not repeat privacy or data-use explanations anywhere else in the app** (no "what is kept" notes, no privacy text on screens); link to `privacy.html` instead. Edit the wording only when asked, bump `CONSENT_VERSION` when you do, and keep it true to what the code and database do (especially deletion).
8. **Accounts:** everyone starts as an anonymous guest; an email can be attached later and the user id stays the same (`account.js`). Account deletion and guest-merge go through RPCs. **Deleting an account keeps the player's data anonymously**: `delete_my_account` (`docs/retain_after_delete.sql`, run by hand in Supabase) erases the sign-in, email, profile, palate and trophies, but keeps journal entries, swipes, photos, own wines, quiz and game answers and feedback, with `user_id` emptied and a random `retired_key` added; `deleteMyAccount` in `data.js` only takes back photos shared for the catalog. **Deleting an entry, swipe or photo only hides it from the player** (`deleted_at`, `docs/soft_delete.sql`, run by hand in Supabase): the database functions mark the row, the views the app reads skip hidden rows, `data.js` reads of those tables filter on `deleted_at`, and photo files are never erased. Nothing a player gives us is removed. Keep the consent text and the delete screen in `account.js` in step with this.
9. **Permissions:** editor/owner capabilities come from `my_staff_access` (permissions such as `catalog_edit`, `quiz_verify`, `feedback_read`, `found_online_photos`). Feature tiers (e.g. the `proTasting` grid) come from `feature_access`. UI gating is convenience only; **RLS in the database is the real enforcement.** **`docs/ROLES_AND_ACCESS.md` is the one definition** of accounts, modes, plans and the four roles (Player, Quiz reviewer, Editor, Owner) and `access.js` is its code: ask `access()` in `app.js` about permissions, never test a label such as "Owner" (convention 23).

10. **Card gestures and accessibility (Discover).** Swipe right / left / up answers (like / dislike / had); double-tapping near the right / left / top edge does the same; the thumbs-down, Skip and thumbs-up buttons are visible under the card, with "I've had this bottle" as a small button below them. Two fingers pinch-zoom the card (up to 4x), a double-tap on the middle (or the Zoom button) zooms in and out, and **while zoomed, swiping and edge double-taps are paused** and one finger pans; the Reset zoom chip returns. All of this lives in `attachCard` in `app.js`. Do not reintroduce `user-scalable=no` in the viewport.
11. **Settings are per device**, kept in `localStorage` under `wine.settings` (text size, answer by swiping, buttons under the card, motion). Swiping off forces the buttons on. **Every font size in the stylesheet is written `calc(Npx * var(--ts))`** so the Text size setting scales it; keep doing that for new CSS. Delete my account is reachable from Settings and still from Profile, Overview (the consent text names that path; see `docs/PRE_TEST_REVIEW.md`).
12. **Games tab / Wine Bingo.** Games is the first place for games (Bingo is the first; more are planned, none are specified yet). A bingo square fills when the player **rates** a wine (a journal entry with a verdict) that matches the square's test; **one wine can fill every square it fits** (a white wine from the USA fills both White and USA); three in a row clears a card; clearing 3 cards of a tier opens the next. Progress is **derived from the journal** each time; only which cards were cleared is remembered on the phone (`wine.games`). Squares are data (`CARDS` in `bingo.js`) and may only test facts the app already holds (style, verdict, country, place, grape, name text, age); never guess a wine's facts. Tier 4 ("draft") names specific vineyards and growths: those lists are facts that an editor must verify before testers rely on them (see `docs/PRE_TEST_REVIEW.md`). A filled square shows a photo only if it is the player's own journal photo or a catalog photo whose kind is in `LICENSED_IMAGE_KINDS` (`bingo.js`); **`found_online` photos are never shown there**. A filled square's details have a **View my rating** button that opens that wine's rating sheet. An empty square offers (1) a wine already in the journal that only needs rating (a Rate it button), else (2) up to three catalog wines from different angles, picked by `recommend.js`. There is no double-tap on bingo squares (it was hard to use); keep it that way. **`recommend.js` is the shared "recommend a wine from the player's profile" feature**, built on the Discover deck's taste model (`deck.js` `userModel`, `prefOf`, `famOf`). It has **lenses** (`LENSES`): `confident` (Safe bet: fits on most fronts), `unique` (Something different: rare, rare grape, unusual for its style; price counts quietly and is never named), `challenge` (A stretch: untried grapes, regions, countries), `similar` (More like this: needs a `seed` wine) and `value` (Everyday pick). Call `recommend({ lens, ... })` for one lens or `recommendMix({ lenses, ... })` for one wine per lens, with `accept`, `exclude` and `limit`; add a lens by adding one entry to `LENSES`. Reasons are built only from the player's history and catalog data; never invent them. Do not use the CSS class `ph` for headings (it is the 72px photo placeholder); games use `gh`.

13. **Owner page** (`owner.js`, opened from Settings for the owner only; `isOwner()` in `app.js` asks `access()` for the `owner_page` permission, convention 23). Tabs: **Wines** (table of the live catalog with search, sortable headings, an issue filter, a tag filter, inline **Reach** and **Price** edits, and "Edit all" which opens the full wine editor; **tick boxes** with "Tick all N shown" (every matching wine, not only the 400 listed) and **mass edits** on the ticked wines: add or remove a tag, set reach (`bulkBar`, `ownerWines` in `app.js`); ticking only redraws the row and the count, so the table keeps its place), **Lenses** (the five recommendation lenses, their weights, and a preview of each lens for the owner or for a brand-new player; the weights are **tried out only, never saved**), **Bingo** (how many catalog wines can fill each square), **Checks** (catalog problems, each linking to the filtered Wines tab), **Tags** (convention 17), **Legend** (convention 21), **Roles** (convention 23) and **Config** (the `app_config` numbers, editable). Edits write through `data.js` (`saveWineReach`, `saveAppConfig`, `saveWinePrice`); a save the database refuses is shown as a failure, never as saved. The UI gating is convenience; RLS is the real enforcement. Lens weights live in `DEFAULT_WEIGHTS` in `recommend.js`; making them editable for real needs a place in the database to store them (not built).

## Domain model as implemented

- **Catalog:** `producers`, `wines`, `wine_vintages` (vintage or non-vintage), `wine_grapes`, `grapes`, `geo_areas` (country → region → appellation tree), `wine_images` (kinds include official, found online, verified user), `wine_reference_values` (structure baseline), `wine_source_records`, `sources`.
- **Designation (DOC, DOCG, AOC …) is kept on the place, not on the wine** (owner, 2026-10-15; all versions): `geo_areas.classification` of the place a wine points at (an appellation, or a region such as Rioja DOCa); the card shows it next to the place (`cardFromRow`). Editors pick it from country-based chips (`DESIGNATIONS`, `designationChoices` in `geo.js`) in **Edit wine info** (`designationRowHtml` in `wineinfo.js`, shared with the venue review): the place's own designation always wins ("From our place list"); **otherwise it is filled in automatically from the stored rule list** (owner, 2026-10-15; `KNOWN_DESIGNATIONS` and `ruleDesignation` in `geo.js`: Leithaberg -> DAC, Barolo -> DOCG, Napa Valley -> AVA; only places whose designation is the same for every wine there, and only the most specific part of the place decides; **an editor must check the list**, and `docs/geo_designations_fill.sql`, generated from it, fills existing empty places once); otherwise a term written in the name is suggested (`designationFromText`); a new place gets it on creation (`savePlace(..., { classification })`), an empty existing place is filled through `fill_place_designation` (`savePlaceDesignation` in `data.js`; `docs/geo_classification.sql`, run by hand; until then the wine still saves and the message says so); **a place that already has one is never changed from a wine's form** (`designationPlan` reports the conflict). Changing a set designation is done by hand in SQL by the owner. **What may be a place (owner, 2026-10-15; all versions; `geo.js`):** a new place's name never holds a classification word (`placeNameProblem`: a designation typed at the end is moved to Designation, "Kamptal DAC" -> Kamptal + DAC, `splitDesignation`; a rank or vineyard classification such as Grand Cru, Erste Lage, Grosse Lage, GG, 1ÖTW or Kabinett is refused, since it stays in the wine name). **Germany and Austria: only broad wine regions are places** (`BROAD_PLACES`: Germany's 13 regions; Austria's four regions and its wine areas and DACs); the village and vineyard ("Wehlener Sonnenuhr", "Ried Heiligenstein") stay in the wine name, `broadPlace` cuts a suggested place down, and `planPlace` refuses to create anything else there. Germany has no place designation (its quality words stay in the wine name); Austria's is DAC. Places already in the database are never changed by these rules.
- **Names are never rewritten; match keys only find (owner, 2026-10-15; all versions).** `text.js` is the one place that says when two names count as the same: `caseKey` (accents and capitals ignored, hyphens and punctuation count; for "does this place or producer already exist"), `plainKey` (also ignores punctuation; for lookups such as flavours, tags, Bingo and the import match) and `matchKey` (also reads St./Ste./Sta. as Saint/Sainte/Santa; only for suggesting and search). Do not add another local fold helper; import these. **What is stored and shown is exactly what an editor typed or the official spelling**: accents, hyphens and legal abbreviations ("Sta. Rita Hills", required by TTB) are kept. A typed name that only looks like one in the list gets a **"Looks like ... already in our list" question** (`lookalikes`, `lookalikeHtml` in `wineinfo.js`: Use it / Keep mine as new); the app never swaps names silently. **One "same wine" rule**: `sameWine` and `wineIdentity` in `catalog.js` (same producer and wine name, type, place, and label grapes; a named wine with grapes missing on one side still counts), used when a wine is added and, through `strictKey`, for "Same wine, different vintages".
- **The place list is tidied by the owner, one suggestion at a time (owner, 2026-10-15; all versions).** `placeChecks` in `geo.js` lists findings on the Owner page, Checks tab, "Places": official spellings that differ from what is stored (`OFFICIAL_SPELLINGS`, each with its source and `confirmed` only when a source was read: St.-Julien -> Saint-Julien per INAO; St.-Joseph and St.-Émilion marked "To check"), places filed at the wrong level (`REGION_LEVEL`: Mosel is one of Germany's 13 regions), appellations straight under a country ("level to confirm", no change suggested), look-alike names under one parent, classification words in names, and places no wine uses. **Legal names are never flagged** (`LEGAL_NAMES` with sources: "Sta. Rita Hills", the official AVA name since 2006 per TTB; "American", a legal US appellation of origin, 27 CFR 4.25). **Apply** calls `apply_place_fix` (`applyPlaceFix` in `data.js`; `docs/place_fixes.sql`, run by hand: owner only, refuses a name already there, every change logged in `place_changes`, wines keep the same place id); **Dismiss** only hides it on that phone (`wine.placeDismissed`). Add a finding by adding a line, with its source, to those lists.
- **Reference lists live in the database, with the code as fallback (owner, 2026-10-15; all versions).** `docs/reference_lists.sql` (tables) and `docs/reference_lists_seed.sql` (generated by `node docs/reference_lists.mjs` from the code lists; run both by hand): `grape_aliases` (`shortcut` = typing help from `grapes.js`, `synonym` = the same grape under another name from `rules.js`, used only to find the grape's rules; a label keeps its own word), `producer_aliases` (spellings an editor confirmed with "Use it"; offered as "Looks like ..."), `place_designation_rules` (`KNOWN_DESIGNATIONS`) and `broad_places` (`BROAD_PLACES`). Each row has `status` (suggested | in use | checked), `basis` and `checked_at`; **only rows in use or checked are used** (`applyReferenceLists` in `app.js`, through `setPlaceLists` in `geo.js`, `addGrapeSynonyms` in `rules.js`, `addGrapeShortcuts` in `grapes.js`, `setNameAliases` in `text.js`); without the tables the built-in lists stay. The owner edits them on the **Owner page, Lists tab** (Use, Mark checked, Remove, Add); editors may add aliases. New synonyms (Lemberger, Kékfrankos) start as suggested. When a code list changes, regenerate the seed.
- **Wine tags (owner, 2026-10-15; all versions; `docs/wine_tags.sql`, run by hand):** the owner's own labels on catalog wines: `wine_tags` (names; only the owner, `settings_edit`, makes, renames or deletes them; none to start) and `wine_tag_links` (on the **wine**, so every vintage carries it; the owner and editors, `catalog_edit`, put them on and take them off). **Labels only for now: nothing in the deck, games or suggestions reads them** (the owner will decide later; `docs/ARCHITECTURE_PLAN.md` §15). They are not wine facts. Managed on the Owner page, Wines tab (Manage tags, tag filter, Tags column, mass add/remove: `loadWineTags`, `addWineTag`, `renameWineTag`, `deleteWineTag`, `tagWines` in `data.js`; `withTags`, `shownWineRows` in `owner.js`). Without the script the tab says the update is needed and the other tools still work.
- **Encountered vs. consumed are separate tables:** `encounters` (swipes and interest changes) versus `consumptions` (drank it; journal). Perceptions (`perceptions`, per consumption and dimension) and tasting notes are stored separately from verdicts.
- **User-owned data:** `user_wines` (wines outside the catalog), `my_wine_info` (private per-player overrides that never change the catalog), `journal_photos` (private; optionally shared for editor review via `photo_candidates`/submissions).
- **Learning:** `quiz_questions`, `quiz_answers`, `timed_runs`, archive views, `content_flags`.
- **Structure dimensions in code:** acidity, body, tannin (1–5 sliders); sweetness, CO₂, oak (fixed choices). Defined in `logic.js` `DIMS` and mirrored by the database. Styles: red, white, sparkling, rosé, fortified.
- **Five verdict codes** (same as DB `verdict_types`): `buy`, `drink`, `none`, `respect`, `no`. Labels are in `logic.js` `VERDICTS`. `respect` ("Dislike, but understand its position") is deliberately weighted far less negatively than `no` in `deck.js`/`profile.js` (-0.5 vs -2): it must not teach the model that the person dislikes the whole category.
- **Reference structure is a baseline, not a "correct answer."** Editor scores win, then rules (`rules.js`), then defaults (`structure.js`). Players do not see structure sliders. They describe taste conversationally (`feel.js`) and the app derives perception.
- **Price:** players enter price paid on their own journal entry. `pricing.js` blends an editor "typical price" with player-entered prices only once enough different players have contributed. Price is not shown as a defining trait of a card.

## Prototype vs. product vision (known differences)

**Swipe model (current; changed by the owner on 2026-10-10 and reworded on 2026-10-12; the earlier three-answer model is saved as `backup/deck-v1-three-answers`, see `docs/VERSIONS.md`):** swipe right is a **thumbs up** (stored as `like`), swipe left is a **thumbs down** (`dislike`), and **Skip** (stored as `dont_know`; it was "I don't know it") is a button under the card (not a swipe). The buttons show thumb icons (`ICONS` in `reactions.js`, `answerFace` in `views.js`), with Skip written out. **I've had this bottle** is kept (swipe up, the top-edge double-tap, and a small button) because it adds the wine to the journal. There is no "Not interested" or "I recognize it" any more. Every answer is saved by `record_reaction` (`docs/reactions.sql`, run by hand in Supabase) as one `encounters` row with a `reaction` (`like` | `dislike` | `dont_know` | `had`) and a small `context` note (`{ tier, fam, pref, skip }`, what the deck knew when it showed the wine); the old familiarity and interest columns are filled in too (`LEGACY_OF`) so the first version can still read the rows. **Thumbs up and down count toward the palate profile and the deck** with provisional weights (`SWIPE_WEIGHT` in `reactions.js`, from `app_config` keys `swipe_like_weight` and `swipe_dislike_weight`: the owner is still deciding the distribution; a journal rating weighs -2 to +2). **Skip carries no palate weight at all.** It does other things: it marks the grapes, places and producers the player has not met (`model.unk`, `gapsOf` in `deck.js`, for recommendations and quizzes to read), it pushes similar wines down the deck (`skipOf`, `unknown_demote_strength`), and a few of them are still spread through the deck about one every `unknown_teach_every` cards (never removed: meeting them is how a player learns). **Skips are counted** (`skip_count` on `v_user_wine_state`, `docs/skip_count.sql`, run by hand after `reactions.sql`; until it is run the app counts the skips it sees itself): **the first skip puts the wine back in the deck, later (the second half of it); the second skip (`SKIP_LIMIT`) takes it out for good** (`skipComesBack`, `skipsOf`, `buildDeck`). Older answers (no `reaction`) never come back. "Put back" in the Swipes tab hides the swipe, so the wine starts fresh. Swipes made before this model (no `reaction`) are read by `reactionOf` as before and carry no palate weight. Quizzes read it through the question tags (convention 17). Not yet present: a pre-consumption *prediction* entity, a community-perception layer with privacy thresholds, a separate market-observation system, a bottle scanner, challenges, and native apps. Treat these as roadmap items, not bugs, and do not add them unasked.

## Product rules that constrain every change

- **Source of truth is verified structured data. AI assists, never decides.** Do not add code that has an LLM invent wine facts, infer flavor/quality/style/grape/vineyard age/production method from names, artwork, or marketing text, calculate the core preference model, or auto-publish factual content.
- Only two kinds of information may become authoritative wine data: **(1) explicit on the bottle** and **(2) inferred by a defined, stored rule** (e.g. appellation → country/region/classification/grape). Anything else is unverified and must stay out of authoritative fields. Keep provenance (source, verified date, status).
- **Keep these separate; never merge into one object:** wine identity, market price, user purchase, user preference, user perception, community perception, wine knowledge, educational content.
- **Preference ≠ perception ≠ understanding ≠ knowledge ≠ exposure.** A user can have high Bordeaux knowledge, low exposure, unknown preference.
- **Real bottle photographs only** as the official image. Never generate or substitute AI images of real wines. The design relies on photos *less*: the Discover deck does **not** prefer or require wines with photos (removed from `deck.js`), and the Discover card shows **no bottle photo at all**, only the drawn bottle silhouette from `visuals.js`. Catalog bottle photos appear only as small thumbnails in the Swipes and Journal lists (`bottleThumbHtml` in `views.js`); a player's own journal photo wins over the catalog photo there. Do not reintroduce photo-based ordering or filtering unasked. User photos stay in the user's journal unless verified through the editor flow.
- Do not invent requirements (monetization, subscriptions, ads, pricing restrictions are **not** in scope). Missing decisions go in the open-questions list in `docs/ARCHITECTURE_PLAN.md`.
- Community statistics must only appear with enough data to be meaningful and privacy-preserving (the prototype uses database-configured minimums via `app_config`).
- Images/data from third parties require researched and validated licensing. Do not assume a provider exists. The current `winelinks.js` only builds web image-search links; it does not license or store images.

## Working in this repo

- **Branching:** develop on the branch you are assigned; do not push elsewhere. Do not open a PR unless asked.
- **Commits:** short imperative subjects (see `git log`). The project has a single contributor so far.
- **Verification:** there is no test suite or linter. After edits, at minimum run `node --check <file>` on changed modules and sanity-check imports and `?v=` versions with grep. For pure modules you can import them in Node (`node --input-type=module -e "import('./logic.js').then(m=>console.log(Object.keys(m)))"`), noting that `?v=` suffixes in relative imports of other files may need to be handled. If you add tests, keep pure files pure so they stay testable, and say clearly that you added the harness.
- **Do not** commit secrets, add a build tool, introduce a framework, or reorganize the flat file layout without being asked. A migration plan (e.g. to a native client) is described in `docs/ARCHITECTURE_PLAN.md`.
- Keep user-facing copy conversational and in everyday words. **Avoid wine-specific jargon in most of the app** (e.g. the review question is "Did the wine taste as expected?", not "Was the wine balanced?"). Wine terms belong in Learn, the professional tasting grid and the Editor. When you change a question's wording, note that internal field names (e.g. `balanced`) stay as they are because they are stored data.
- **Speed rules (2026-10-09).** Start-up asks for independent data at the same time (`enterMain`, `loadAllCards`, and the public reads started early by `startEarlyLoads`/`once`); do not add a new `await` in a row where a `Promise.all` would do. Opening a tab never waits for the network: `refreshInBackground` (at most every 30 seconds, and again after a swipe or any other change) fetches behind it and redraws. `owner.js` and `demo.js` are imported on first use (`loadOwnerModule`, `loadDemoModule`), so keep other code from importing them at the top of `app.js`. The Discover counts come from `countSwipesAndJournal` in `data.js` and leave out hidden rows.
- **Saved versions** are frozen backup branches described in `docs/VERSIONS.md` (the first is `backup/deck-v1-three-answers`, the Discover deck with the three answers before it was changed). Never push new work to a `backup/` branch, and do not delete one; add a new one when the owner asks to save a version.
- Before testers are invited, work through `docs/TEST_BEFORE_TESTERS.md`; keep it current when you add features that need a database script or a live check.
- When a request depends on a database change, or on an external provider, license or API that has not been confirmed, state that dependency explicitly instead of coding around it.
- **Ask first whether a change is for one version or all (owner, 2026-10-15).** Before planning a change that touches the database or shared catalog data (the main app and venue branches such as `vwm` share one database), ask the owner whether it is for that venue only or for every version. Shared changes are made on the main working branch first and then merged into the venue branches.

15. **This or That** (`thisorthat.js`, screens in `games.js`, the second game on the Games tab). The player is asked only about **food or everyday things**; **wine is never named in a question**. Each pick carries a `lean`: a structure line from `DIMS`, or the **`world` line (Old World vs New World, from the wine's country via `WORLD`, a defined rule)**. The results say what the picks lean toward in everyday words and list up to 3 catalog wines that point the same way (`structure.js` `structureMap`, or the country for `world`). **The results screen shows two pictures side by side, line by line** (`compareHtml` in `games.js`): the player's own taste from their rated journal (`palateAxes` and `tasteForGame` in `profile.js`: the same numbers as the Profile Taste page, plus a "where from" line worked out from each wine's country) on the left, and their This or That picks (`axisValues`) on the right, with a sentence on where they agree or differ (`compareAxes`). A journal line needs at least two rated wines; otherwise it is drawn empty. The leans are a game's guess, **not wine facts and not a measure of the player**. They **never feed the Discover deck or taste model**. Picks are kept on the phone (`wine.thisorthat`) **and saved to the database for the owner's research**: table `this_or_that_answers`, one row per player and pair, written by `saveThisOrThat` in `data.js`, row built by `answerRow` (no name, email or wine; see `docs/this_or_that.sql`, which must be run in Supabase by hand). **The rows are kept when an account is deleted, anonymously**: each carries a random `player_key`, and deleting the account turns `user_id` to null (`on delete set null`), cutting the only link to a person. A failed save never blocks the game. **The pair list is meant to grow** (the owner wants more input so the game says more about a wine taste profile; see the note above `PAIRS`), so never show a count of pairs or picks on a screen. Add a pair by adding one entry to `PAIRS` (`kind: "other"` for non-food); keep the list ordinary and the difference clear. The consent and privacy wording covers this data.

16. **Import wines into the journal** (`importer.js`, opened from the Journal tab's "Import wines from a file", loaded on first use like `owner.js`). The player chooses a CSV file or pastes rows, checks the detected columns (`detectMapping`), sees what will happen, and confirms; `importJournal` in `data.js` saves the entries. **Only what is in the file is used; nothing is guessed about a wine.** A wine whose producer, wine name and vintage exactly match a catalog wine (accents and case ignored) is linked to the catalog. **Every other wine becomes the player's own wine (`user_wines`), and wines only join the catalog through the existing candidate flow (`catalog.js`: enough players' entries for the same wine, then an editor approves it as "pending review"), never straight from an import.** Wines already in the journal, or listed twice, are skipped. **Row limit per file: 100 for everyone, 500 for Editors and the Owner (the `import_extended` permission; a Quiz reviewer gets 100) and for tiers listed in the `importLarge` feature switch (`feature_access`; the tier is named `pro`; `docs/import_tier.sql`).** **The limit is enforced in the database** (`docs/import_limit.sql`, run by hand in Supabase): a trigger on `consumptions` and `user_wines` refuses new rows over the player's allowance within a window (defaults 100, or 500 for `import_extended` holders and `pro`, per 24 hours; `my_import_limit` reads the permission since `docs/roles_proposal.sql`; the numbers are `import_limit_regular`, `import_limit_extended` and `import_window_hours` in `app_config`, editable on the Owner Config tab), reading tier and staff access from `profiles`/`feature_access` (players cannot edit `tier`, `role` or `staff_role`: the `profiles` update grant covers only name and consent columns). The page asks `my_import_allowance` for what is left (`importAllowance` in `data.js`) and falls back to its own 100/500 rule until the script has been run; a refusal from the database stops the import and is shown once. **The rating-to-answer rule (`RATING_RULE`) is ON HOLD** (`USE_RATING_RULE = false`): ratings in a file are ignored, imported wines arrive unrated, and the rating column is not shown; the owner will revisit it before testing. Entries use origin `manual`, no photos, no structure ratings. Do not add privacy text to the sheet (see convention 7). **Reminder: importing from other apps (Vivino, CellarTracker and similar) must be tested with real exports before friends and family try the app** (see `docs/TEST_BEFORE_TESTERS.md`).

17. **Quiz tags and the Swipes tab view (2026-10-10).** `docs/quiz_tags.sql` (run by hand in Supabase) adds `quiz_tags` (kind: grape, region, country, producer, style or theme; seeded from `grapes`, `geo_areas`, `producers` and the five styles) and `quiz_question_tags`. **Editors** (`quiz_verify`) tag a question in the Editor's question sheet (`review.js`): the app suggests 5 to 10 tags (`suggestTags` in `tags.js`: whole-word matches in the question and answers, filled up from tags popular for the topic) and the editor ticks the right ones (no limit on suggested ones) and may add **at most two more from the pull-down per edit** (`MAX_PULLDOWN`, `canPull`); the Quiz list shows each question's tag count and has a "No tags" filter. **Only the owner** (`settings_edit`) adds tags (Owner page, Tags tab, `addQuizTag`); a new tag joins the suggestions and the pull-down at once. Tags are **not wine facts about the player**; they only say what a question is about, and the loader works without the script (questions open and save, the tag part says the update has not been run). A tag's key (`tagKey`) is the same `kind:name` key the Discover deck uses, so `learn.js` asks questions tagged with something the player said "I don't know it" to a little sooner (`gapWeights` of `gapsOf`, `boostFor`, `weave`: every other unseen question, never only those). **Swipes tab** (`swipetabs.js`, drawn by `swipesHtml` in `views.js`, choices in `state.sw`): **one row of icons**: thumbs up, thumbs down, skip, All (each with its count) and a "..." button; the search, group, sort and type controls are **hidden until that button is tapped** (a dot on it shows a filter is on), and the default is a flat newest-first list; the All tab has a Show filter; each tab can be grouped by grape, region, country, producer, type, vintage or how well the wine fits the player (`prefOf`, worked out only when used) and has search, a type filter and a sort; a group opens to its wines. The search box redraws only `#swList`. Do not add a count of anything the owner has not asked for.

18. **Voice notes and incomplete wines (2026-10-13).** The Journal has **Take a note** (`quickNoteHtml`, `quickNoteAction` in `app.js`): the player speaks (browser speech recognition in `dictation.js`; feature-detected, so without it the box is typed, or uses the phone keyboard's microphone key) or types, and the words are saved **as they said them, with the time** (`composeNote` in `notes.js`) as a journal entry (`addQuickNote` in `data.js`); the rating sheet's notes box has **Speak your notes** too. **Nothing is read out of a note: no AI or rule picks grapes, places or any wine fact from the words.** The browser may send the audio to its maker's speech service: `privacy.html` needs a line about it (owner and lawyers; not added yet; do not add privacy text elsewhere). **Incomplete wines:** a wine the player typed in may be saved with only a producer or a name. **`isComplete` in `catalog.js` is the one place that says what complete means** (a producer, a vintage year or NV, and a type of wine; `missingFields` names what is missing). Incomplete wines stay in the player's own journal and are **never** catalog candidates (`groupSubmissions`), Bingo squares or community numbers until completed; the Journal shows "Incomplete: needs ..." on them, an **Incomplete (n)** filter chip, and the pencil opens "Change wine info" to finish them. Saving a wine with no producer needs `docs/incomplete_wines.sql` (run by hand: it lets `user_wines.producer` be empty); until then the app says so. Any database view or function that lists candidates must skip rows with no producer. **Microphone permission:** `dictation.js` asks for it itself (`askMicrophone`: the browser's own "Allow microphone?" question, then it lets go of the microphone; `microphoneState` checks what the browser already knows) the first time the player taps Speak, because a page that never asks can look blocked; later taps start at once. A refusal is explained in plain words with the steps to allow it (the browser never lets a page ask again after a "Block"; the player has to switch it back on in the browser's site settings). It needs an https page. **The microphone being allowed and the browser's speech recognition being allowed are different things** (iPhone browsers have a Dictation switch and a Speech Recognition permission): an error from the recognition after the microphone was allowed is explained as a speech problem (`SPEECH_OFF`), or, right after the first Allow, as "Tap Speak once more" (some browsers use up the tap on the question); it is never reported as a blocked microphone. A refused first try is retried once with the gentlest settings; if the browser still will not turn speech into text (the iPhone home-screen app and some in-app browsers never do), the notes box is focused so the **keyboard's own microphone key** can dictate (`reason: "speech"` in `onError`). **Speech to text that works in every browser would need a transcription service behind a server function (a provider, a key, a cost, and a line in `privacy.html`): not built; the owner has not chosen one.** **Every error ends the try**: the button goes back to Speak, an old error is cleared on the next tap, and stopping always ends in off even if the browser never sends "end" (`reset`, `fail` in `dictation.js`; `showMic` in `app.js`).

19. **Who is this for: Beginner / Enthusiast / Professional (2026-10-13).** A per-device Settings choice (`mode` in `wine.settings`, default Beginner). **It changes words and which extra tools show; never data.** `words.js` holds the wording (`say("key")`, one entry per key with a word for each mode; a missing word falls back to Beginner, so add wording a little at a time; the current mode is set by `applySettings` through `setMode`). Wine terms belong in `words.js` for Enthusiast and Professional, not in everyday text (convention above). **Enthusiast and Professional** also show the Journal's extra tools (`proToolsOn`): **Blind tasting** and **Export my notes**; they only handle the player's own data, so they need no tier (the `proTasting` grid stays tier-gated). **Blind tasting** (`blind.js`, the sheet in `views.js` `blindHtml`, flow in `blindAction` in `app.js`): the player writes a guess (type, grape, country, region, vintage) and notes (spoken or typed), may save it on the phone (`wine.blind`) to reveal later, then picks the wine (a catalog wine or one typed in); the reveal compares the guess **only with facts the app already holds** (`scoreGuess`: right, close, not this time, not guessed, not on record) and the result line goes into the wine's rating-sheet notes with the time. Nothing about a wine is worked out from a guess. **Export** (`exportcsv.js`) saves the player's own journal as a CSV (formula-looking cells are protected with an apostrophe). Do not tie new wording to a tier. **Practice a topic** (Enthusiast and Professional, Learn tab): a "Focus" pick above the quiz limits a round to the questions editors tagged with one grape, place, producer, style or theme (`focusOptions` and `refOf` in `tags.js`, `focus` in `poolFor` in `learn.js`), listing the topics the player has met least first (`gapWeights`); it needs `docs/quiz_tags.sql`, and the pick simply does not show without tags.

20. **Wine words in dictation (2026-10-14).** Speech recognition is tuned for everyday English, so dictated notes get three free helps. **(1) Word check** (`termfix.js`, pure): after the player's words are finished (never while talking), words and groups of up to three words are compared with a vocabulary (`buildVocab`: the grape list `GRAPES`, the catalog's own producers, cuv\u00e9es, appellations, regions and countries, and the curated Italian, French, German, Spanish and tasting words in `winewords.js`, the one place to add words) and near misses are corrected to the real spelling (`fixTerms`, `matchGroup`: edit distance plus a rough sound key). **It only fixes the SPELLING of the player's own words from known lists; it never adds a fact.** An ordinary English word is never changed (`COMMON` in `termfix.js`: add to it if a real word is ever "corrected"). Right spellings in the wrong form (case, hyphen) are fixed silently; close fixes are applied **and listed as chips under the notes box** (tap to put back what was heard, tap again to re-apply: `wfix` in `app.js`); weaker matches are only offered as "Did you mean ...?". **(2) Biasing:** where the browser supports `SpeechRecognition.phrases` the wine on screen, the journal's wines and the wine words are passed in (`biasPhrases`, `dictation.js` `options`); skipped silently elsewhere. **(3) Speak in:** a picker (`speakLangHtml`, `lang` in settings, `SPEECH_LANGS`) for notes spoken wholly in Italian, French, Spanish or German; the default follows the phone. A different language for the whole session makes English parts worse, which is why mixed notes rely on (1) and (2). A server transcription service with a custom vocabulary would be better still and is not built (needs a provider, key, cost and a `privacy.html` line).

21. **Notes fill the professional tasting grid, and the legend grows (2026-10-14).** For players with the grid (`state.pro`), the notes in the rating sheet are read into the grid (`gridFromNotes` in `notegrid.js`): right after dictating or typing (about a second after the last change), when the grid opens, and from **Fill from my notes** in the grid. **It reads only the player's own words and fills the player's own grid; it never changes facts about the wine, and no language model decides anything.** Unclear words leave the answer empty (two different answers at the same strength cancel; "not tannic" is understood but not turned into an answer; plain "cherry" goes to the group "red fruit", not "red cherry"). **The player's taps always win** (`mergeFromNotes` never overwrites an answer); answers that came from the notes are **marked** (dashed outline, "from your notes: <words>", count on the rating sheet), a tap on one makes it the player's own (`touched`), **Clear what was filled in** removes only those, and an answer the player pushed back on is not put back in that rating (`tastingBlocked`). **The legend** is what makes it grow, three layers matched strongest first: the player's own words (`note_legend_mine`, and answers they pushed back on, `rejected`), the shared legend editors and the owner approve (`note_legend`), and the seed in `notelegend.js` plus the level patterns in `notegrid.js` ("high acidity", "long finish", "full-bodied"). Words that matched nothing are listed as **"Words I could not place"**; tapping one asks what it meant (any line of the grid valid for the wine's type, `legendEntry` checks it: 1 to 4 plain words, no digits, links or addresses) and the player's legend learns it at once. Optionally the player shares the **word and answer only (never a note, a wine or a name)**; the owner reviews suggestions on the **Owner page, Legend tab** (how many different players suggested each, `legend_candidates()`; approve, reject, remove, or add a word directly). Nothing is learned silently: every line comes from a player's explicit pick or an owner's approval. **Needs `docs/note_legend.sql`** (run by hand): until then the starting legend works and the player's own words are kept on the phone (`wine.legend`). `privacy.html` needs a line about the optional sharing of words (owner and lawyers; not added). The grid is a professional-tier feature (`proTasting`); the fills follow the same gate. Add starting words in `notelegend.js`; editors' review of suggestions is on the Owner page only for now.

22. **Working offline (2026-10-14).** The app opens and works with no connection, in a browser tab and installed. **Photos are online-only.** Layers: `sw.js` (registered as `sw.js?v=N`, N read from `app.js?v=` in `index.html`; keeps the app's own files, files with a `?v=` are served from the copy first, `index.html`/`config.js`/`privacy.html` network first; a capped set of public bottle thumbnails; it never touches the database), `vendor/supabase.js` (the pinned library, loaded first with the CDNs as fallback; update steps are in its header), `offline.js` (framework-free; IndexedDB, with memory as fallback). **`offline.wrap(client)` wraps the Supabase client in `app.js`, so every read and write must keep going through `state.sb`/`data.js`; do not create another client or call `fetch` for data.** Reads are saved on every success and returned from the saved copy when offline. **Writes are online-only unless marked with `.queue(effect)`** (the `tag(q, effect)` helpers in `data.js`, `learn.js`, `tasting.js`); the effect (`overlay.js`) says how the queued change shows up in the journal, swipes, counts, quiz progress and tasting notes until it uploads. Inserts that return an id get a temporary `tmp_...` id which the replay swaps for the real one everywhere; replay is in order, stops on a network error, treats a duplicate (23505) as done, and moves a refused change to the "could not upload" list (Settings, with Try again / Drop it), never dropping it silently. The queue is capped (`maxQueue` 1000). **To make a new write work offline: mark it with `.queue(effect)` and add its effect to `overlay.js`; leave staff, owner, editor, sign-in, import, account and photo writes online-only** (they get a "needs a connection" message). **Release rule: bump `?v=` on every changed module and `app.js?v=` in `index.html`; that also makes a new service-worker cache and removes the old one.** Sign-out and account deletion clear the saved copy and queue (`offline.clearAll`); the guest carry-over waits until the queue is empty; a different person signing in on the phone clears the old copy. Nothing secret is stored (the same public key as before). Only about 30 tiny (~100 px, 2 MB cap) journal photo thumbnails are kept for offline viewing. Swipes made offline are dated at upload (order kept). `privacy.html` needs a line about the device copy (owner and lawyers; not added). In an iPhone browser tab the system may erase site data after about a week unused: the chip shows "N changes waiting" and a one-time tip suggests adding the app to the home screen.

25. **Guess the Glass (2026-10-14).** The third game on the Games tab (`blindgame.js`, pure; screens in `games.js` `guessScreen`; wiring in `app.js` `startGuess`, `guessFollow`, `guessWines`). The player reads a wine's **profile** and picks from four choices; five modes: **Full blind** (grape and place), **Which grape?**, **Where from?**, **How old?**, **How does it feel?**, each a round of 5 at Easy or Hard (Hard picks the closest wrong answers by `similarity`). **Every clue comes from a stored rule or the catalog**: flavors from the grape and place rules (`clueFlavors`: the grape's **hallmark** notes first (`HALLMARKS`, only flavors already in that grape's list), then its rarer notes, never a winemaking note (`WINEMAKING`: vanilla, toast, butter, cedar, chocolate, brioche; a sparkling wine keeps its yeast notes) because those point to oak or method, not a grape; oak is told by the feel sentence instead and the Why says so); faint notes only fill up to three, feel from `startingValues` (an editor's score wins), climate from `climateOf`, grape, place and vintage year from the card; the profile reads as one short paragraph (`profileText`, `feelSentence`, clue words in bold); **the climate is never named in it: it is told through the fruit** (`RIPENESS`: cool = tart, zippy, just-ripe; mild = fresh, ripe; warm = ripe, juicy; hot = jammy, cooked; Full blind and Where from? only), and the Why says what that ripeness points to. The professional tasting grid has the same idea as a **Fruit ripeness** line (`fruitRipeness` in `tasting.js`: under-ripe, just ripe, ripe, over-ripe, with a hint; not a structure line, so it moves no slider) and the notes can fill it (`notelegend.js`: "tart fruit", "jammy", "cooked fruit" ...) and is labelled typical, never facts about a bottle. Questions come from `CLASSICS` (well-known grape and place pairs the rules already know; add one there, only with a grape and place in `flavordata.js`/`rules.js`) and catalog wines with one known grape. **"Vintage" means the characteristics that come with age** (owner's choice), not good or poor years: `AGE_CUES` (colour, smell and taste, feel per type and band: Young 1-3, Developing 4-9, Mature 10+), `GRAPE_AGE` (what some grapes show with age) and `AGE_POTENTIAL` (drink-young grapes are never asked as Mature); a catalog wine's age comes from its vintage year, a classic is given a band. Words for the feel follow the Beginner / Enthusiast / Professional mode (`FEEL_WORDS`; kept in this file so `words.js` and its importers did not change). After each answer: **Why** (each line repeats a rule), **Learn it** (up to 2 quiz questions about the answer's grape, place or "Wine ageing", answered in place and saved as ordinary quiz answers through `learn.answerOne`; found by tags first, then whole words, `questionsAbout` in `learn.js`), a **More about ... in Learn** button (`learn.focusOn`: a round on just those questions with a "Topic / Show all" chip, for every mode) and **Try a wine like it** (`recommend.js` "Safe bet" with `cardFitsTopic`, never a wine the player rated or turned down). The result screen lists the missed topics with Learn buttons and wines to try. **The game never touches the palate, the deck or the taste model and writes nothing to the database** (except Learn it's quiz answers); best scores stay on the phone (`wine.guess`).

26. **Venue version (branch `vwm`, Vintage Wine Merchants, 2026-10-14).** This branch is the app for one shop; the main working branch has none of this code. **"VWM" is internal only** (branch, `venue_id`, code, docs); every screen says **Vintage Wine Merchants** (Discover header, page title, home-screen name in `manifest.webmanifest`, the Owner tab). `venue.js` (pure) holds `VENUE` (the one line another venue branch changes) and the list rules. **Every place that picks catalog wines to show or suggest uses only the venue's list** (`venueCards()` in `app.js`): the Discover deck (`buildDeck` gets `pool`; the taste model still reads the whole journal), Bingo square help, This or That wines, Guess the Glass (venue wines only, no classics: `buildItems(..., { classics: false })`) and its wines to try. **The player's own record stays catalog-wide** (adding a wine they drank, typing one in, import, blind tasting, their journal and swipes, Learn, Editor and Owner tools); `state.cards` stays the full catalog. With an empty or unloaded list the deck shows "Vintage Wine Merchants' selection is being prepared" and never falls back to the whole catalog. **The list** lives in `venue_wines` (`docs/venue_decks.sql`, run by hand; everyone reads, only `settings_edit` writes; online only) and is managed on the **Owner page, "Vintage Wine Merchants list" tab**: upload or paste the shop's file (two layouts: Producer / Wine name / Vintage columns matched exactly like the journal import, or the shop's one-column **Title** export, `parseTitle`/`matchTitle`: same vintage and every word of a catalog wine's producer and wine name in the title, the more specific wine wins, a tie is left for a hand pick), preview, save; add or remove wines by hand; **Re-check** links rows once editors have added the wine to the catalog. Non-wine lines (spirits, sake, glassware, books, non-alcoholic; `isWine`) are left out. **No catalog wine is ever created from the shop's file alone**: rows not in the catalog wait as "not in our catalog yet" until an editor reviews them in the **Editor tab, section "Vintage Wine Merchants"** (`venuereview.js`, `catalog_edit`): one row at a time, laid out to fit on one phone screen, and **sorted by country, region and producer** so one producer's wines come one after another (rows with no country last). **The form is filled from `vwmprep.js`**: suggestions worked out ONCE (2026-10-15) from the titles of the list as uploaded then (2021 titles), by fixed word rules only (producer split, type, place as appellation/region/country, label grapes, and a "probably not a wine" flag for spirits); the file is **unverified, says so in its header, and is loaded only on that screen**. Titles not in it (a later upload) get the app's own suggestions (`suggestRow` in `venue.js`: the longest catalog producer the title starts with, label words for the type, the longest `geo_areas` name in the title, grape names). **The editor checks and changes every field**: tap the last word of the producer's name, type chips, a **searchable place** (`searchPlaces`: every typed word must be in the place's full name, "St." read as "Saint"; or **Type a new place** as appellation / region / country, created when the wine is added with `savePlace` in `geo.js`; `canonPlace` takes a place from the list only when it is the same name (accents and capitals aside); a name that only looks alike is offered as "Looks like ... already in our list" (`placeLookalikes`, `producerLookHtml`: Use it / Keep mine as new), never swapped; the screen says what will be created), the place is cut down to the broad region for German and Austrian wines (`broadPlace`, see "What may be a place"; the village and vineyard stay in the name), a **Designation** row under the place (the shared `designationRowHtml`; the place's own designation wins, else the term in the shop's title, kept on the place, see "Designation" in the domain model), vintage and grapes. **The wine name leaves out what fills its own fields** (owner, 2026-10-15; `wineNameOf` in `venue.js`): grape words that are in the grapes field and place words that are in the place field (with the place's DOC/AOC term; **a rank such as Grand Cru, Premier Cru or Riserva always stays in the name**, owner 2026-10-15) are taken out of the name, when the form is filled, when the producer split is tapped and when a place is picked; the name may end up empty. **An existing wine is reused for another vintage only when its name, type and place agree, and its label grapes too** (a named wine with no grapes on record still counts; `addVenueCatalogWine`), so one producer's "Grand Cru" from Corton and from Chambertin, or "Trimbach Riesling" and "Trimbach Pinot Gris" (both unnamed), never become one wine. Then **Publish now**, **Add for review** (`addVenueCatalogWine` in `data.js`: reuses an existing producer, wine or vintage, records the source "Vintage Wine Merchants list" with the shop's title, and links the list row), or **Skip**; only the owner sees **Remove from list**. The list is read 1000 rows at a time (`loadVenueList`), since the shop's list is longer than one read. `venue_wines` lets editors update rows (to link them) but not add or remove them. **Older vintages (owner, 2026-10-15):** when the list holds several vintages of the same wine, **only the most recent one is shown** (the deck, games and suggestions: `venueCardsOf` drops `olderVintageIds`, using the catalog's own "same wine" rule, `duplicateGroups` in `catalog.js`; non-vintage wines are never "older"). **The older ones are not removed**: they stay on the list and in the catalog for the record, and the Owner tab marks them "Older vintage: kept on record, not in the deck". Archiving in Editor, Catalog is no longer needed for this. **Website links (owner, 2026-10-15):** on the venue deck the wine name links to **the wine's own page on www.vintagewinemerchants.com**, never to a web image search; **a wine with no page on the shop's website gets no link at all** (`c.shopUrl` set by `venueCards()` from `linkMap` in `venue.js`; `cardHtml` in `views.js`). Links are kept on the list rows (`venue_wines.product_url`, `link_status`, `link_checked_at`; `docs/venue_links.sql`, run by hand; the database refuses any address off the shop's site). They are found and checked by the server function **`venue-links`** (`docs/venue_links_function.js`, deployed by hand, steps in `docs/VENUE_LINKS.md`; a browser cannot read another site): **Find links** matches a row to the shop's catalogue only on the same title and vintage with one clear answer (`matchProduct`), else leaves it unlinked as "Not on the website"; **Check links** opens each saved page and **removes** links that are gone (404/410, or sent to the home page) or now show a different wine (`pageMatches`); a page that could not be reached is left as it was. Both buttons are at the top of the **Owner page, Vintage Wine Merchants list** tab (`mountLinks`) and in the Editor tab, Vintage Wine Merchants, behind the **Website links: find and check** button (`linksHtml`, `runLinks` in `venuereview.js`); the Owner list shows a Website column. **Check links never removes links when the website is misread**: the function reads a page's title from the shop's product data (`<page>.json`) or from the page head only (the payment-card icons in the body carry titles such as "American Express"), and the app stops a check, removing nothing, when 3 or more pages in a batch seem to show the same title. The function only reads the website and never writes to the database; the app saves the results (`venueLinks`, `saveVenueLink` in `data.js`). Online only. **The Owner list tab manages the deck (owner, 2026-10-15)**: Website links box first, then the list with a **Show** filter (`LIST_FILTERS`, `filterListRows` in `venue.js`: in the deck, not in our catalog yet, not published, older vintages, linked, not on the website, link removed, not looked for, and by wine tag), a Tags column, and per row: the website page typed by hand (`siteUrl`: only a page on the shop's site; an emptied box marks the wine not on the website), **Edit wine** (the full wine editor; it changes the catalog wine in every version), **Review** (opens the Editor tab's review on that row, `openRow`) and Remove. **Tick boxes and mass edits** (`venueBulkBar`, `ownerVenueRows` in `app.js`): Find links and Check links for the ticked rows only (`runLinks(kind, ids)`), Not on the website, Clear link (Find looks again), add or remove a wine tag (catalog wines only), Remove from list (asks first; `removeVenueRows`, `saveVenueLinks` in `data.js`). Ticking only redraws the row and the count.
